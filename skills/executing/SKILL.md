# Executing

Turn approved acceptance criteria into committed, reviewed code. The item's `### Acceptance criteria` is the work list: each AC is an outcome plus its verification, and every brief, report, review verdict and progress note cites AC IDs. **Executing never edits an AC** — see the pre-flight below. **Route by tier** (HARRY.md §3) — there is no "subagent or inline" prompt; the tier decides.

## Route

```
Trivial   → session mode  (CC does the steps inline, verify, done — no review)
Standard  → session mode  (CC does the steps inline, then ONE mandatory independent review)
Major     → subagent mode (fresh subagent per task + per-task review + final review)
```

State the route in one line before starting ("Trivial → session mode" / "Standard → session mode + review" / "Major → subagent mode"). When in doubt, go higher.

**Re-classify mid-flight.** If scope growth crosses a §3 tier trigger during execution (more files, a new subsystem, a red line surfacing), STOP, re-declare the tier out loud, and adopt the higher tier's remaining gates from that point. Work already done stands — its gates are not re-run retroactively — but the review/TDD gates not yet reached run at the new tier.

## Before either mode

1. **Branch.** A fresh branch for the unit, never `main`/`master` without consent. Session mode works on it in place, at any tier — one writer needs no worktree. A worktree is for concurrent writers, exactly as HARRY.md §5 lists them (subagent mode's parallel units are one case); if any of them is writing in the main checkout already — the user included — isolate instead of branching in place.
2. **Paths.** Every `.local/…` path in this skill means the **MAIN checkout's** store (HARRY.md §5) — a bare relative one written from inside a worktree would create a second store there. Resolve it **inside the same command that uses it**: shell variables do not survive from one tool call to the next, and a subagent's shell never saw yours, so hand subagents the already-resolved absolute path, never the `$STORE` literal.

   ```bash
   STORE="$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")"
   ```

   `$STORE/.local/tmp/<branch>` itself is created by whichever step first writes into it — Standard's review-diff write (session mode step 4) or subagent mode's first brief write (step 1) each run their own `mkdir -p` before writing; Trivial writes nothing here during executing. Finishing step 2's architecture review also writes here (its own `mkdir -p`) and is the first creator for a Trivial unit, since Trivial never runs the writes above.

   (If the project has no `.local/` at all, set it up or confirm it first — HARRY.md §5.)

3. **Pre-flight AC review** (Standard/Major). Read the item's `### Acceptance criteria` once and scan for AC that is wrong, impossible, ambiguous, a step rather than an outcome, missing its verification, or in conflict with another AC or the item's Constraints — a later AC that names the AC it supersedes is not a conflict (`references/doc-types.md`). **You may not fix any of it yourself** — approved AC text is the user's (`references/doc-types.md`). Present every finding as **one batched question**, each quoted beside the AC it concerns, and ask the user to rule; this is the same STOP as the BLOCKED path below. Clean scan → proceed silently.

   **Legacy items.** An in-flight item whose `## Why / What` has no `### Acceptance criteria` is executed from its `## Plan` steps as written — the plan is the work list, and this pre-flight scan has nothing to scan. Record progress the same way, in `## Progress` (or in the plan's own completion notes when that is what the item already uses). Never retrofit acceptance criteria onto it.
4. **Mark started + track progress in the item** (Standard/Major). Add (or update) this unit's line in `.local/INDEX.md` `## In flight` (`<topic> · <branch> · <started YYYY-MM-DD>`; HARRY.md §5). Progress goes in the item's **`## Progress` section** (create it if absent) — **append-only**, one line per event, each citing the AC IDs it covers and the commit range, so it survives compaction. Never edit approved AC text to record progress. An AC with a complete line is DONE — do not re-dispatch it; a resumed session reads `## Progress` and resumes at the first AC without one — in subagent mode only after step 5's **Resuming** check of surviving task worktrees, which a session runs whenever it resumes the unit: a new session, or the same one after compaction. Trust `## Progress` and `git log` over recollection.

   **The report file is a log** (subagent mode). A task's report file (`<store>/.local/tmp/<branch>/<task id>-report.md`, step 2) is append-only, one entry per event: `## dispatched <round>`, which the session appends before every dispatch or resume of the task; `## result <round>`, which the implementer appends after its last commit, opening with its status; and, for every per-task review (step 3, and each re-review in steps 4 and 5), `## review <round>: dispatched`, which the session appends before dispatching the reviewer, then `## review <round>: clean` or `## review <round>: findings` (the open-findings list) once it accepts the report. `<round>` is `initial` (again for a task the user sends back from **Resuming** to step 2, to implement it again), `fix round <R>/4` (an integration fix included) or `needs context`. Each review attempt writes its report to its own file, `<store>/.local/tmp/<branch>/<task id>-review-<k>.md`, where `<k>` is one more than the number of review files the task already has — never reused; a report the session sends back is re-dispatched as a new attempt. The log is evidence, not state: people read it, and step 5's **Resuming** shows its last entries when it asks, but no rule routes on it.

## Session mode (Trivial / Standard)

CC executes inline on the unit's branch (§5: one writer, no worktree). No implementer subagent.

1. Do the work — satisfy the AC list in order / make the obvious change.
2. Verify — run it, read the output (exit code, failures), then claim (HARRY.md §6). No "should/probably."
3. **Trivial:** no review — → **finishing** skill.
4. **Standard: mandatory independent review** (compensates for inline execution). Leave one runnable check (HARRY.md §6). Package the working diff (`merge-base..HEAD` or the uncommitted diff) to a file under the store's tmp dir (resolve `$STORE` per the Paths rule, `mkdir -p "$STORE/.local/tmp/<branch>"` before this first write), then dispatch **ONE** CC reviewer subagent (explicit `model: opus` — the §5 dispatch cap; never inherit the session model) with the diff + the item's `### Acceptance criteria` (and its Constraints, when it has them) + `references/review-rubric.md`. Do not pre-judge findings or tell it what not to flag. **Accept its report only with BOTH verdicts** — spec AND quality; the spec verdict is per AC, with evidence (`references/review-rubric.md`); one missing verdict is not a valid review, so send it back rather than read a partial report as a pass. Fix Critical/Important findings with the session as fixer. A small fix (HARRY.md §3) gets the full suite, no re-review, and one `## Progress` line, `AC-<n>: small fix: <what> (commit <sha7>)`; the suite is its only check, since Standard has no later diff review. When a round has both kinds, its small fixes join the loop's fix range and are re-reviewed with it. Any other fix takes the loop: each re-review is **scoped** — the fix-range diff plus the open-findings list, per-finding verdict ADDRESSED / NOT ADDRESSED, new breakage inside the fix diff joins the list, anything outside it → the item's `## Follow-ups`, never the loop. **Cap: three fix rounds**, then adjudicate each still-open finding with a recorded ruling (contestable → ruling appended to `## Progress`; real-not-load-bearing → `## Follow-ups`; load-bearing → BLOCKED to the user; a silent discard is a §6 violation). New findings in the same area (same file or same rule) in two consecutive review rounds → stop and ask the user whether the scope still serves the unit's goal; name the goal (HARRY.md §6). Record each round in `## Progress` (`AC-<n>: fix round <R>/3: <X> addressed, <Y> open (commits <base7>..<head7>)`) — a unit whose last `## Progress` line is a fix round resumes mid-loop. Minor findings → `## Follow-ups`, triage before finishing. Then append the AC complete lines to `## Progress` and → **finishing** skill.

## Subagent mode (Major)

Implementer = **CC's own subagents** (not an external delegate). Each gets isolated, precisely-built context — never your session history — via **file handoffs**, plus an explicit output contract. A task is one AC, or a group of AC that must land together. Tasks with data/interface dependencies run sequentially; independent tasks default to parallel dispatch, each in its **own** worktree (HARRY.md §5), cut from the unit's branch and named by the session itself (step 2) — never a harness isolation worktree, which is cut from elsewhere and named by the harness, so git would not identify it as the unit's. While any parallel task is in flight, every task — a sequential one too — runs in its own worktree branched off the unit branch, so no writer shares the unit branch's checkout with step 5's fast-forward (HARRY.md §5); and a task still writing in the unit branch's checkout finishes before any parallel task is dispatched. The task stays in its worktree through its review and fix rounds, and reaches the unit branch only through step 5's integration, never before. A task's worktree never outlives the task that made it: step 5 owns the rest of its lifecycle; finishing finds task worktrees and refs only by step 2's naming rule — at a Discard, and at cleanup for any a run left behind.

**Parallel dispatch reads `## Dispatch`.** When the item has that section, it governs: one row per unit gives the AC covered, the write set (dispatch only disjoint write sets), what the unit reads from other units, and whether it lands first or last — a cross-unit contract test lands last. A unit that builds against an interface another unit has not written yet is not parallel with it: dispatch it after that unit lands. When the item has no `## Dispatch` and you are about to dispatch 2+ units in parallel, write one now, before dispatching; it is the only record of who owns which files.

**Model by role.** Predictable-nature work routes to a durable role — dispatch it by `subagent_type` and pass **no** `model`/`effort` (the role owns them; an inline arg overrides and defeats the binding): recon → `scout`, mechanical fully-specified edits → `mech`, prose/docs → `writer`, security-sensitive → `security` (HARRY.md §5). Judgment-heavy implementation and fixing have **no** role: dispatch ad-hoc at the **dispatch cap — `opus`** (a HARD cap, HARRY.md §5: session models above it are thinking-class, reserved for the session's own reasoning, never dispatch targets; the cap moves only on the user's explicit instruction — do not vague it to "figure it out at dispatch time"; that made silent session-model fallback too easy), and *there* you MUST set `model` and `effort` explicitly (an omitted model silently inherits the session's — above the cap, a violation; a weaker model flails and burns more turns than it saves — turn count beats token price). The task's *nature* decides role-vs-cap, never tier/file-count — a mechanical Major task (the same field across 8 CRUD files) → `mech`; a subtle 2-file concurrency fix → ad-hoc `opus`. Several small, independent edits of the same kind across files (the same one-line fix, constant change, or field addition) go to **ONE** `mech` dispatch whose brief lists every file and its change, reviewed as one diff — not one dispatch per file. That batched dispatch counts as **one task**: it keeps this tier's test discipline and goes through steps 3–5 (review, fix loop, mark complete) like any other task. A dispatch of its own is for a change that needs its own judgment, its own tests, or its own review surface. Reviewers are routed separately (step 3). **Codex build:** there is no per-subagent dispatch — apply the role's advisory model/effort from the `/sync`-wired role map in `~/.codex/AGENTS.md` (via a session profile, or `-m` plus reasoning-effort config); judgment-heavy work uses that map's most-capable row. With no subagents on that build, the session implements each task itself and appends every log entry, the `## result` ones included, and it is step 4's fixer too: every loop fix still goes through that step's re-review, and round 4's escalation is a switch to the role map's most-capable row — work already on that row has no other fixer: its round 4 is the adjudication, not a fix round; resume works as it does on Claude Code, since no rule routes on the log. **Reviewers on that build:** there are no CC subagents, so the reviewer in step 3 and the CC lane in step 6 are both that build's own review skill (`codex-skills/review`), and step 6's Codex lane collapses into it — the orchestrator reviewing itself is not a second opinion. Record that only one lane ran.

Per task. Each task has a **task id** — its AC ids joined with `-` (`AC-3`, `AC-3-AC-4`); it names the task's files in the store and, in step 2, its branch, worktree and base ref, so git and the store name a task the same way after compaction or in a new session:

1. **Brief.** Extract the task's AC verbatim — IDs, outcome text and each one's verification — to a brief file under the store (`<store>/.local/tmp/<branch>/<task id>-brief.md` — transient, deletable; resolve `<store>` per the Paths rule, `mkdir -p "<store>/.local/tmp/<branch>"` before this first write, and write the absolute path into the dispatch prompt). The dispatch prompt carries: where the task fits (one line), the brief path ("read first — your requirements, exact values verbatim"), interfaces/decisions from earlier tasks the brief can't know, your resolution of any ambiguity, the report-file path + report contract (the report cites AC IDs and says which are satisfied, with the evidence each AC's verification produced), and a **no-subagent contract**: the implementer does the whole task itself and never dispatches subagents — not helpers, and above all never its own reviewer (review comes from the controller after the report, see step 3) — because a worker-spawned reviewer duplicates the controller's review seat at full cost and its verdict counts for nothing. (Role agents mech/writer/security are already tool-enforced leaves; this contract covers the ad-hoc dispatch-cap route.) The brief also carries one rule for the implementer and every fixer: never merge, rebase, reset or pull the unit branch into the task branch — integration is 5.1's job, and a fixer only commits a merge 5.1 left in progress. Exact values live only in the brief.
2. **Dispatch implementer** (model per the routing above). Fresh subagent. A task that gets its own worktree gets it from the session, named from the unit branch and the task id: branch `task/<unit branch>/<task id>`, worktree `<git common dir>/harry-worktrees/<unit branch>/<task id>` (`<git common dir>` is `git rev-parse --path-format=absolute --git-common-dir`: outside every working tree, so tools that scan directories — test runners, `tsc`, watchers — never see a task's copy). Its **base ref**, `refs/harry/<unit branch>/<task id>/base`, holds the branch point. The session creates the branch and the base ref together, in one transaction, then cuts the worktree on that branch:

   ```bash
   base=$(git rev-parse <unit branch>) && printf 'start\ncreate refs/harry/<unit branch>/<task id>/base %s\ncreate refs/heads/task/<unit branch>/<task id> %s\nprepare\ncommit\n' "$base" "$base" | git update-ref --stdin && git worktree add <path> task/<unit branch>/<task id>
   ```

   `create` refuses a ref that already exists, and a refused transaction writes neither, so an existing base ref is never moved and a task with its own worktree always has both refs or neither. `worktree add` failing leaves both refs at the base: fix its cause and run the `git worktree add` alone — never the transaction again. Then dispatch into that path, without harness isolation. Git is the record: `git for-each-ref refs/heads/task/<unit branch>/` and `git worktree list` name the unit's tasks, and `## Progress` gets no line for the dispatch. The transaction refused because either ref already exists → git already holds the task, and **Resuming** has already classified it: stop and ask the user. A re-dispatch reuses the task's base ref and worktree and cuts nothing: the transaction runs only at a task's first start (a missing worktree is cut with `git worktree add` alone). A task that runs on the unit branch itself writes its base ref alone, create-only, at its first start: `git update-ref refs/harry/<unit branch>/<task id>/base <unit branch> ""` — refused the same way → the same rule; a re-dispatch reuses it.

   It implements, follows TDD (red-green + watch-it-fail), tests, commits, self-reviews, appends its full report to the report file after its last commit (`<store>/.local/tmp/<branch>/<task id>-report.md`, absolute in its prompt), and returns only: status, commits, one-line test summary, concerns.
   - Status handling: **DONE** → review. **DONE_WITH_CONCERNS** → read concerns; address correctness/scope before review. **NEEDS_CONTEXT** → provide it, re-dispatch. **BLOCKED** → stop and ask, don't guess (more context / stronger model / split task / escalate). Never silently retry the same model unchanged. An AC that turns out wrong, impossible or ambiguous — yours or the implementer's finding — is BLOCKED too: take it to the user with the AC quoted. Neither you nor a subagent rewrites an approved AC.
3. **Per-task review.** AC compliance + code quality, scoped to this task's diff (write the diff to `<store>/.local/tmp/<branch>/<task id>-diff.patch`; hand the reviewer the brief, the report, the diff, and the item's Constraints verbatim when it has them, plus the absolute path of its review file, where it writes its report). Dispatch **ONE** CC reviewer subagent (explicit `model: opus` — the §5 dispatch cap). Hand it `references/review-rubric.md` itself, not just a citation of it — its reviewer rules only bind a reviewer that has read it. Per-task review is single-lane on purpose: the Codex lane, where the build has one, runs once per unit at the final review (step 6), so a Major spends Codex quota once instead of per task. Do not pre-judge findings or tell the reviewer what not to flag. **Accept a report only with BOTH verdicts** — spec AND quality (`references/review-rubric.md`); the spec verdict is per AC, with evidence, and one missing verdict is not a valid review, so send it back rather than read a partial report as a pass. **Codex build:** no CC subagent to dispatch here — see the Model-by-role carve-out above; that build's review skill names its own report file on its `Review written to` line.
4. **Fix loop — capped at four rounds.** A small fix (HARRY.md §3) to a per-task review finding stays out of the loop when every fix that round is small: the session makes it in the task's checkout (its worktree, when it has one), runs the full suite, and appends `AC-<n>: small fix: <what> (commit <sha7>)` to `## Progress`; no re-review, and step 6 sees it. When a round has both kinds, the round's fixer makes the small fixes too, so only one writer works in the checkout. Any other fix takes the loop below. Integration findings (step 5) always take the loop, under that step's limits. The cap operationalizes §6's three-failed-fixes law: three failures of the same fixer mean the fourth round changes the *fixer*, not the hypothesis; still open after that is structural, so adjudicate instead of looping. **The session is never the fixer inside the loop** (on the Codex build it is: see Model by role) — fixing a finding yourself skips the loop's re-review; every loop fix goes through the loop's fixer below (the resumed implementer in rounds 1–3, the fresh one in round 4). When the task has its own worktree, its fixer — resumed or fresh — works in it, which is still there until step 5 removes it. Give a fresh fixer that worktree's absolute path; never dispatch it with a new isolation worktree, which would be cut from elsewhere and hold none of the task's commits.
   - **Rounds 1–3: resume the original implementer** with the open findings verbatim — its context (task, code, its own choices) makes the fix better and cheaper than a fresh dispatch (turn count beats token price). It fixes, re-runs covering tests, appends a fix report to the same report file and returns the same status contract. No live agent to resume because the session resumed? Step 5's **Resuming** paragraph decides first. When the user, asked by **Resuming**, sends a task back here, dispatch a fresh fixer into its existing worktree (the unit checkout for a task with no task branch) with brief + report file + findings; its round is one past the task's last `fix round` line in `## Progress`, `fix round 1/4` when it has none (a round cut short before its line was written runs again under its own number), and round 4 is still the escalation.
   - **Round 4 — escalation: one fresh implementer**, dispatched with the brief, the report file and the open findings. Role-routed work escalates to the ad-hoc dispatch-cap route (the Model-by-role routing above); work already at the cap gets fresh eyes only. A loop that survives three resumes usually means the implementer cannot see its own problem.
   - **Every re-review is scoped:** diff range = the head the previous review saw → the task's tip now, both named by ref (`git rev-parse --short task/<unit branch>/<task id>`, or `<unit branch>` for a task with no task branch), never read from the session's working directory; when the session no longer holds that head (a new session, or after compaction), the range starts at the base ref unless the user names a head. After an integration, step 5 sets the range. It is handed with the open-findings list. Per-finding verdict **ADDRESSED / NOT ADDRESSED** — attempted is not addressed. New Critical/Important *inside the fix diff* joins the open list; anything outside it → the item's `## Follow-ups`, never the loop.
   - **Still open after round 4 → stop the loop and adjudicate.** Adjudicate each open finding with a recorded ruling — a silent discard is a §6 violation: contestable / reviewer-wrong → park it with a ruling appended to `## Progress`; real but nothing builds on it → `## Follow-ups`; real and load-bearing → STOP, BLOCKED to the human with finding + AC text + fix history. Adjudicate only at the cap — earlier is pre-judging.
   - New findings in the same area (same file or same rule) in two consecutive review rounds → stop and ask the user whether the scope still serves the unit's goal; name the goal (HARRY.md §6).
   - Record each round in `## Progress` (`AC-<n>: fix round <R>/4: <X> addressed, <Y> open (commits <base7>..<head7>)`).
   - Minor findings → `## Follow-ups` for final triage (finishing turns these into new backlog items, as `references/doc-types.md` sets out). A finding that conflicts with an AC → human decides; present the finding beside the AC text, and do not edit the AC to settle it.
5. **Integrate, then mark complete.** This step owns a task worktree's lifecycle from here to its removal. In this step, **Resuming** included, a check that cannot run counts as not passing: stop and ask the user. A task that ran on the unit branch itself — only when no other task is in flight — has nothing to integrate: it skips to 5.4, and 5.5 only deletes its base ref (`git update-ref -d refs/harry/<unit branch>/<task id>/base`).
   1. **Merge in.** Each pass, merge the unit branch into the task's branch in its worktree (`git -C <path> merge --no-ff <unit branch>`) — `--no-ff`, so a task with no commits of its own never fast-forwards onto other tasks' landed work, and `git log --first-parent` never counts their commits as its own. Conflicts → leave the merge in progress and hand them to step 4's fixer as a finding — the session is not the fixer here either. The fixer resolves them and commits the merge — never `git merge --abort`, a reset or a rebase — and makes any other fix in separate commits after it; a fresh fixer's prompt says the worktree is mid-merge. Once the re-review passes, append `AC-<n>[, AC-<m>]: integration: conflicts resolved in <merge7>` (step 6 reviews it again at whole-branch scope), then come back to 5.1.
   2. **Suite in the worktree.** Red → the task is not complete: hand the failure to step 4 as a finding, then come back to 5.1.

      Integration findings run through step 4 under these limits: they continue the task's round count; the fixer stays inside the task's `## Dispatch` write set — a fix that needs another unit's files is BLOCKED; and integration conflicts or a red suite still open at the cap — or arriving after the loop already reached it — are BLOCKED to the user, never adjudicated. Their re-review range is the integration merge's `--remerge-diff` (`git show --remerge-diff <merge7>`, the conflict resolution alone) plus its merge commit → the task's tip now, so other tasks' merged code stays out; when the integration merged nothing, step 4's range.
   3. **Fast-forward.** A task with no commits of its own beyond its base ref (`git rev-list --count --no-merges --first-parent refs/harry/<unit branch>/<task id>/base..<its branch>` is 0 — 5.1's integration merges are not its own) has nothing to land: skip the fast-forward and go to 5.4, whose `<head7>` is then the base ref itself. Otherwise, green → `git -C <unit checkout> symbolic-ref --short HEAD` must print `<unit branch>`; otherwise stop and ask — a fast-forward moves whatever branch that checkout holds. Then `git -C <unit checkout> merge --ff-only <its branch>` (the unit's worktree, or the main checkout for a branch in place), so integration only ever moves the unit branch to a tree whose suite passed. Refused because another task landed meanwhile → back to 5.1; refused for any other reason (a dirty unit checkout) → stop and ask.
   4. **Mark complete.** Append one line to the item's `## Progress`: `AC-<n>[, AC-<m>]: complete (commits <base7>..<head7>, review clean)` — `review clean` only when the last review raised nothing; `review clean after small fixes` when step 4's small fixes closed what it raised; or `review adjudicated` plus the rulings recorded when the loop exited at the cap. `<base7>` is the task's base ref (`git rev-parse --short refs/harry/<unit branch>/<task id>/base`) — the branch point, or, for a task that ran on the unit branch itself, the unit branch's head when the task started — and `<head7>` the head the unit branch landed at: the task branch's tip (`git rev-parse --short task/<unit branch>/<task id>`) when 5.3 fast-forwarded, the base ref (`git rev-parse --short refs/harry/<unit branch>/<task id>/base`) when 5.3 had nothing to land, the unit branch's head (`git rev-parse --short <unit branch>`) for a task that ran on it; `git log --first-parent <base7>..<head7>` lists the task's own commits and integration merges, without what those merges brought in. `## Progress` is append-only, so this record survives into the archive.
   5. **Remove the task's worktree and delete its branch** — only when its task branch is gone or passes the deletion proof; otherwise stop and ask. The **deletion proof**: `test "$(git merge-tree --write-tree <into> <from>)" = "$(git rev-parse '<into>^{tree}')"` (git ≥ 2.38) — merging `<from>` into `<into>` would change nothing. Compare the command's whole output, never just its first line: on a conflict it still prints a tree first, and a modify/delete or binary conflict can leave that tree equal to `<into>`'s. 5.5 runs it with `<into>` = `<unit branch>` and `<from>` = `task/<unit branch>/<task id>`. It compares content, so 5.1's integration merges add nothing, and a conflict resolution kept only in a merge commit counts. Each removal runs only if its target still exists, so 5.5 is safe to re-run: the worktree — if `git worktree list` lists `<path>`: when its directory exists, it must pass the **clean check** first — `git -C <path> status --porcelain -uall` empty and `git -C <path> rev-parse -q --verify MERGE_HEAD` printing nothing (if not, stop and ask); ignored files are not listed: a task worktree holds only agent-made files whose work is committed; then `git worktree remove <path>`, which removes only that registration, even when the directory is already gone; then the branch and the base ref together, in one transaction, only after the worktree is gone (`update-ref` does not refuse a branch a worktree still holds), and deleting a ref already gone is a no-op:

      ```bash
      printf 'start\ndelete refs/heads/task/<unit branch>/<task id>\ndelete refs/harry/<unit branch>/<task id>/base\nprepare\ncommit\n' | git update-ref --stdin
      ```

   **Resuming.** Whenever a session resumes the unit — a new session, or the same one after compaction — and before it dispatches anything, it reads the unit's task worktrees from git — `## Progress` does not record them. Walk each task that has a branch under `refs/heads/task/<unit branch>/` or a base ref under `refs/harry/<unit branch>/` (`git for-each-ref`), with its worktree from `git worktree list`; a worktree, branch or ref outside those prefixes is not this unit's: leave it untouched. Classify every task before acting on any, from git and `## Progress` only — the report log is evidence to show the user, never a row's condition. Each task takes the first row that fits:

   | State | Action |
   |---|---|
   | A complete line, and its task branch gone or passing the deletion proof (5.5) | run 5.5 |
   | Anything else — no complete line, even on a task 5.3 already fast-forwarded, or a complete line on a task branch that fails the deletion proof | stop and ask the user |

   Only the run-5.5 row continues on its own: **Resuming** never re-dispatches a task. A task in any other row is not resumed by inference: git and `## Progress` cannot show where it stopped, or whether an agent is still working on it. Stop and ask the user, showing its branch, its commits beyond the unit branch (`git -C <path> log --oneline <unit branch>..HEAD`), whether a merge is in progress (`git -C <path> rev-parse -q --verify MERGE_HEAD`), its `status --porcelain -uall`, its last `## Progress` lines, the log's last entries, and the unit branch's reflog (`git reflog show --format='%h %gs' <unit branch>`), which tells 5.3's fast-forward from an agent's own sync; the user names the step it resumes at — step 2, step 4, 5.1 or 5.4. A base ref without a task branch is a unit-branch task: step 2 creates a task's branch and base ref in one transaction, and 5.5 and finishing's Discard delete them in one, so a task with its own worktree has both or neither; a unit-branch task that resumes finishes before any parallel task is dispatched. Executing never deletes a base ref before its task's complete line: it is where that line's range starts. A task git holds nothing for resumes by `## Progress` alone (Before either mode, step 4).

   Do not check in with the human between tasks — work the whole AC list; stop only for BLOCKED or genuine ambiguity (a consequential, hard-to-reverse design choice the AC didn't settle).

After all tasks:

6. **Final review — two lanes, once per unit.**
   - **CC lane:** one broad whole-branch CC reviewer subagent, dispatched as in step 3 — hand it `references/review-rubric.md` itself, not just a citation of it, same as step 3. A whole-branch pass has no per-task brief, so its dispatch prompt carries the item's `### Acceptance criteria` **verbatim** — all of them, IDs and verifications — in the brief's place, plus the item's Constraints when it has them, and every integration conflict resolution recorded in `## Progress` (its merge commit), named for review again at whole-branch scope: the task's loop saw each only against its own task. Package the full branch diff (`merge-base..HEAD`) to a file. **Codex build:** no CC subagent to dispatch here — on that build both lanes are the review skill, see the Model-by-role carve-out above; record that only one lane ran.
   - **Codex lane** (a reviewer that is not the orchestrator — a fresh, ephemeral `codex exec review` process, not the CC session reviewing itself). Two steps, both from the unit's branch checkout (its worktree, or the main checkout for a branch in place):

     1. Write a facts file at `<store>/.local/tmp/<branch>/review-context.md` holding an `## Acceptance criteria` section with the item's AC **verbatim** (this lane judges spec against the same list as the CC lane), then this unit's binding constraints, the rulings recorded so far, each with its reasoning, and the merge commits where integration resolved conflicts — **facts only**, never verdicts and never "don't flag X" (the `/harry:review` `--context` contract, `commands/review.md`). Resolve `<store>` in the same command that writes the file, per the Paths rule, and have that command also print the resulting absolute path — it does not survive to the next call, so paste the printed value literally into step 2.

     2. Invoke the slash command (via the `SlashCommand`/`Skill` tool, not `Bash` — it is not a shell command) with that printed absolute path:

     ```
     /harry:review --base <base-branch> --context @<absolute path printed in step 1>
     ```

     `/harry:review` runs `codex exec review` read-only and writes findings to a
     fresh `<store>/.local/tmp/<branch>/codex-review-<YYYYMMDD-HHMMSS>.md` per
     run, reporting that path on `Review written to <path>` — **read that file**:
     the lane's findings only exist there. It picks the reviewing model from
     `~/.codex/config.toml`, not from this skill.

     No `Review written to` line plus a no-changes `# Review Summary` means the
     branch has nothing to review — record that in `## Progress`; it is not a
     lane failure.

     If the lane fails (auth, model, quota, or any other error), record the
     verbatim error in `## Progress` and take it to the user — never silently
     skip it, never claim it ran.

   Merge whatever lanes ran into **one** findings list before acting, deduped, noting which lane raised each — that record is what later tells you whether the cross-model lane earns its quota. Findings → **one** fix subagent with the complete list (not one fixer per finding). Point it at the item's `## Follow-ups` to triage what must be fixed before merge. After that fix wave lands, run exactly **one scoped re-review** of the fix range (step 4's re-review rules) — fixes to this review's findings are never small, so the last code on the branch is never left unreviewed. **There is no second fix wave:** residuals are adjudicated the same way as subagent mode step 4's round-4 cap (park with a recorded ruling / `## Follow-ups`; load-bearing → BLOCKED, surface at finishing).
7. → **finishing** skill.

## Follow-ups discovered during execution

A follow-on task that surfaces mid-execution (out of scope for this item, but
worth doing later) is appended as one line under the item's `## Follow-ups`
section (create the section if it doesn't exist yet) — not a new file, and
not a code `DEBT:` marker (those stay code-side per HARRY.md §4; a
`## Follow-ups` line is for process/scope-level follow-on work, a `DEBT:`
marker is for an in-code shortcut with a ceiling). `finishing` turns these
into new backlog items on completion — do not create backlog items directly
during execution.
